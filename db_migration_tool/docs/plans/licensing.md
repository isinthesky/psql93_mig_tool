- **대상**: 신설 `src/licensing/`, `src/main.py`, `installer/DBMigrationTool.iss`, 신설 `tools/issue_license.py`

- **선행 조건**: 없음

## 1. 요구사항 (확정)

| 항목 | 결정 |
|---|---|
| 목적 | 고객사 계약 기간 제한 |
| 만료 시 동작 | **제한 모드** — 새 마이그레이션만 막고 재개·검증·조회는 허용 |
| 복제 방지 | **계약으로 통제.** 기술적으로는 설치본 이미지 복제만 막는다(§4) |
| 동시 사용 | **허용.** 같은 키를 여러 대에 입력해도 막지 않는다 |
| 키 입력 시점 | 인스톨러 설치 단계 (1단계로 끝낸다) |
| 기존 배포본 | **대응하지 않는다.** 1.0.0/1.2.1 사용자가 새 버전으로 올리면 미인증 → 제한 모드 |

기간 제한이 본질이라는 점이 이 설계의 성격을 정한다. 대수 제한이나 유출 차단을
기술로 강제하지 않기로 했으므로, 복잡한 사전 바인딩과 2단계 발급 절차를 들이지 않는다.

동시 사용까지 허용하므로 TOFU가 남기는 효과는 **설치본 폴더를 통째로 복사해 뿌리는 것을
막는 것 하나**다. 그것만으로 유지하기로 했다(§4.1의 기대치 표를 참고).

## 2. 핵심 위험 — 반드시 먼저 이해할 것

### 2.1 만료가 데이터를 중간 상태로 방치할 수 있다

이 앱은 수천만 행을 체크포인트 기반으로 나눠 옮기고, 중단되면 다음 실행에서 재개한다.
**만료로 앱이 열리지 않으면 재개 경로가 사라진다.** 소스와 대상이 어긋난 채 남고,
사용자에게는 복구 수단이 없다. 라이선스가 데이터 정합성 사고의 원인이 되는 것이다.

그래서 이 계획은 다음을 못박는다.

- 라이선스 검사는 **앱 시작 시 1회만** 한다. 실행 중 재검사하지 않는다.
- 마이그레이션이 도는 도중 만료일이 지나도 **그 실행은 끝까지 간다.**
- 만료 후에도 **재개·검증·이력 조회는 항상 열어 둔다.**

이 세 가지를 어기는 구현은 반려한다.

### 2.2 exe는 보호 장치가 아니다

PyInstaller 6.x는 bytecode 암호화를 지원하지 않는다(`--key`는 4.x 이후 제거됨).
`pyinstxtractor`로 `.pyc`를 뽑아 검증 분기를 뒤집는 데 수 분이면 된다.

**따라서 이 설계의 목표는 "정직한 사용자가 계약 기간을 넘겨 쓰거나 다른 PC에 퍼뜨리는 것을
막는 것"이지, 악의적 크래킹 방지가 아니다.** 후자를 요구하면 네이티브 확장, 온라인 검증,
서버측 실행 등 지금과 다른 아키텍처가 필요하다.

### 2.3 오프라인에서 키 재사용은 막을 수 없다

PC에 묶으려면 키에 머신 ID가 들어가야 하는데, **설치 전에는 그 PC의 머신 ID를 모른다.**
그래서 사전 바인딩은 "설치 → 등록 코드 전달 → 키 수령 → 입력"의 2단계 절차를 강제한다.

이 계획은 1단계 절차를 택했으므로(§1) 사전 바인딩을 쓰지 않는다. 그 결과:

**같은 키 문자열을 여러 PC에 입력하면 전부 활성화된다. 이것은 막지 않는다.**

활성화 상태를 공유할 서버가 없으니 각 PC는 서로를 알 수 없다. 온라인 활성화라면
서버가 대수를 셀 수 있지만, 폐쇄망 고객사에서는 쓸 수 없다. 이 한계를 받아들이고
대수·유출은 계약으로 통제한다.

## 3. 라이선스 키 설계

### 3.1 서명 방식

`cryptography`가 이미 의존성에 있으므로 **Ed25519**를 새 패키지 없이 쓴다.
대칭키(Fernet)는 쓰지 않는다 — 앱 안에 키가 있으면 사용자가 라이선스를 위조할 수 있다.

- **개인키**: 개발사만 보관. **저장소에 절대 넣지 않는다.**
- **공개키**: `src/licensing/keys.py`에 상수로 내장. 노출돼도 위조에 쓸 수 없다.

### 3.2 페이로드

```json
{
  "v": 1,
  "cust": "고객사명",
  "iss": "2026-08-05",
  "exp": "2027-08-04",
  "lic": "8f3a2d71"
}
```

- `exp`: 만료일(포함). 이 날짜까지는 정상 동작한다.
- `lic`: 라이선스 일련번호. 발급 대장과 대조하고 로그에 남긴다(키 전체는 로그에 남기지 않는다).
- 머신 ID는 페이로드에 **넣지 않는다**(§4의 TOFU 방식 채택 시).

### 3.3 키 문자열 형식

사람이 메일·메신저로 옮겨 적고 인스톨러에 붙여넣어야 하므로 Base32(대문자+숫자, 혼동 문자 없음)를 쓴다.

```
DBMT1-<payload_b32>-<signature_b32>
```

5자씩 하이픈으로 끊어 표시하되, 검증 시에는 하이픈·공백·대소문자를 무시하고 정규화한다.
붙여넣기 사고를 줄이기 위함이다.

## 4. PC 바인딩 — TOFU 채택

**TOFU(Trust On First Use)**를 쓴다. 첫 실행한 PC를 정당한 PC로 받아들여 기록하고,
그 뒤로는 달라지면 거부한다. SSH가 처음 본 호스트 키를 `known_hosts`에 적어 두고
다음부터 바뀌면 경고하는 것과 같은 구조다.

동작:

1. 인스톨러가 키를 받아 저장한다. 이 시점에는 서명만 유효하고 아직 어느 PC에도 묶이지 않는다.
2. **첫 실행 시** 머신 ID를 계산해 활성화 레코드를 만든다. ← 여기서 PC가 정해진다
3. 이후 실행마다 기록된 머신 ID와 현재 값을 대조한다. 다르면 `WRONG_MACHINE`.

### 4.1 무엇을 막고 무엇을 못 막는가

기대치를 정확히 적어 둔다. 나중에 "복제가 되던데"라는 말이 나오지 않도록.

| 시나리오 | 결과 |
|---|---|
| 활성화된 PC의 `%LOCALAPPDATA%` 폴더를 통째로 다른 PC에 복사 | **차단** (머신 ID 불일치) |
| **키 문자열을 알아내 다른 PC에 새로 설치·입력** | **통과 — 막지 않는다** |
| 같은 키로 여러 대에 설치 | **전부 동작 — 막지 않는다** |
| `.activation` 삭제 후 재실행 | 같은 PC면 재활성화되어 정상. 다른 PC로 옮겨도 재활성화된다 |
| 만료일 경과 | 차단(제한 모드) |
| 시스템 시계 되돌리기 | `last_seen` 역행으로 감지 (파일을 지우면 초기화됨) |

**즉 TOFU가 실제로 막는 것은 "설치본 이미지를 떠서 뿌리는 것"뿐이다.**
키 재사용은 §2.3에서 정한 대로 계약으로 통제한다.

이 정도로 충분하다고 판단한 근거는 §1이다 — 목적이 계약 기간 제한이고,
대수 제한은 기술로 강제하지 않기로 했다.

### 4.2 머신 ID

Windows에서 안정성과 접근성을 함께 만족하는 조합:

```
machine_id = SHA256(
    HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid   # 비관리자도 읽기 가능, OS 재설치 시에만 변경
  + C: 볼륨 일련번호                                     # 포맷 시에만 변경
)[:16]
```

- MAC 주소는 **쓰지 않는다.** USB 랜·도킹·가상 어댑터로 수시로 바뀐다.
- WMI(메인보드 UUID 등)는 **쓰지 않는다.** 호출이 느려(수백 ms~초) 시작 시간을 해친다.
- VM을 sysprep 없이 클론하면 MachineGuid가 복제된다. 여기서는 문제가 되지 않는다 —
  애초에 키 재사용을 막지 않기 때문이다.

하드웨어 교체·OS 재설치로 머신 ID가 바뀌면 `WRONG_MACHINE`이 된다.
**이때 사용자가 스스로 풀 수 있어야 한다** — §8.2 참조. 공급사에 연락해야만 복구되는
설계는 만들지 않는다. 기간 제한이 목적이지 사용자를 묶어 두는 게 목적이 아니다.

## 5. 저장 위치

인스톨러가 `PrivilegesRequiredOverridesAllowed=dialog`라 **비관리자 설치를 허용**한다.
따라서 `HKLM`은 쓸 수 없다.

| 파일 | 위치 | 내용 |
|---|---|---|
| 라이선스 키 | `%LOCALAPPDATA%\DBMigrationTool\license.key` | 실제로 쓰이는 키 (앱이 기록) |
| 활성화 레코드 | `%LOCALAPPDATA%\DBMigrationTool\.activation` | 머신 ID 해시, 첫 실행 시각, 마지막 실행 시각 |
| 씨앗 | `<설치폴더>\license.seed` | 인스톨러가 남긴 초기 키. 앱이 첫 실행에 위로 옮긴다(§9) |

두 파일 모두 사용자가 지울 수 있다. **위조는 서명으로 막는다.** 삭제는 파일마다 다르게 처리한다.

| 지운 파일 | 결과 |
|---|---|
| `license.key` | 미인증 → 제한 모드 (§6의 `MISSING`) |
| `.activation` | 유효한 키가 남아 있으면 현재 머신 ID로 **재활성화**되어 정상 동작 (§6의 TOFU 분기) |

`.activation`을 지우는 것으로 PC 바인딩을 풀 수 있다. 이것은 §4.1에서 이미
수용한 한계다 — 막아 봐야 하드웨어 교체 시 사용자가 갇히는 사고만 남는다.

파일을 숨기거나 난독화하지 않는다 — 효과는 없고 백신 오탐만 늘린다.

기존 `.encryption_key`와 같은 디렉터리를 쓰므로 `AppPaths`를 그대로 재사용한다.

## 6. 검증 흐름

`src/main.py`의 `main()`에서 **DB 초기화 직후, `MainWindow` 생성 전**에 수행한다.
DB보다 먼저 하면 안 된다 — 만료 안내에도 이력 조회를 열어 줄 것이므로 DB가 필요하다.

```
license.key 읽기
  없음 → 미인증
서명 검증 (Ed25519, 공개키 내장)
  실패 → 위조/손상
활성화 레코드 확인
  없음 → 현재 머신 ID로 생성 (TOFU)
  있음 → 머신 ID 대조, 불일치 시 다른 PC
시계 역행 확인
  마지막 실행 시각 > 현재 시각 → 시계 조작 의심
만료일 확인
  exp >= 오늘 → 정상
  exp <  오늘 → 만료
마지막 실행 시각 갱신
  last_seen ← max(last_seen, now)      ← 반드시 단조 증가
```

마지막 줄이 `max`인 것이 중요하다. 역행을 감지한 실행에서 `last_seen`을 조작된
과거 값으로 낮춰 쓰면, 두 번째 실행부터는 역행이 사라져 검사가 스스로 무력해진다.
값을 낮추지 않으면 시계를 되돌려 둔 동안 계속 만료로 잡힌다.

결과는 다섯 가지다.

| 상태 | 앱 동작 |
|---|---|
| `VALID` | 전부 허용 |
| `EXPIRING` (만료 30일 이내) | 전부 허용 + 시작 시 경고 배너 |
| `EXPIRED` | **제한 모드** |
| `MISSING` / `INVALID` | 등록 창 표시, 등록 전까지 제한 모드 |
| `WRONG_MACHINE` | 제한 모드 + "다른 PC에서 활성화된 라이선스" 안내 |

미인증도 **차단이 아니라 제한 모드**로 둔다. §2.1의 재개 경로를 지키기 위함이다.

### 6.1 시계 역행

`.activation`에 마지막 실행 시각을 남기고, 그보다 과거로 돌아가면 만료로 간주한다.
완전하지 않다(파일을 지우면 초기화된다). 정직한 사용자의 실수와 단순한 시계 조작만 잡는 수준으로 본다.

## 7. 제한 모드의 정의

**허용** — 데이터를 안전한 상태로 만드는 데 필요한 모든 것

- 앱 실행, 프로필 조회, 이력·체크포인트 조회, 로그 확인
- **중단된 마이그레이션 재개** (기존 `history_id`에 대한 이어하기)
- 행 수 검증(`RowCountVerifyWorker`)
- 아카이브 무결성 확인

**차단** — 새 작업을 벌이는 것

- 새 마이그레이션 시작 (`MainWindow.start_migration`에서 새 실행 경로)
- 새 프로필 생성

프로필 **편집은 막지 않는다** (계획 단계에서는 차단 대상이었으나 구현에서 제외).
DB 암호가 바뀐 채 중단된 작업을 재개하려면 연결 정보를 고칠 수 있어야 한다 —
편집을 막으면 §2.1이 못박은 재개 경로가 끊기고, §2.1을 어기는 구현은 반려 대상이다.

구현 지점:

| 위치 | 처리 |
|---|---|
| `MainWindow.start_migration` | 제한 모드면 안내 후 마법사를 열지 않는다. 단, 미완료 이력이 있으면 **재개 전용으로 연다.** |
| `MigrationWizardDialog._set_run_state` | 제한 모드 + `resume_mode=False`면 시작 버튼 비활성 + 사유 툴팁 |
| `FileArchiveMigrationDialog` | 동일 |
| `MainWindow` 상태바 | 라이선스 상태와 만료일 상시 표시 |

`resume_mode`가 이미 있으므로 재개/신규 구분에 새 개념을 만들 필요가 없다.

## 8. 발급과 운영

### 8.1 발급 도구 — `tools/issue_license.py`

```bash
python tools/issue_license.py --cust "OO전자" --months 12 --key-file <개인키경로>
python tools/issue_license.py --cust "OO전자" --exp 2027-12-31 --key-file <개인키경로>
```

- 개인키 경로는 **인자로만** 받는다. 저장소·환경변수 기본값을 두지 않는다.
- 발급 내역(일련번호, 고객사, 만료일, 발급일)을 CSV로 append 한다. 이 파일도 저장소에 넣지 않는다.
- 키 생성: `python tools/issue_license.py --genkey` → 개인키/공개키 쌍 출력. 공개키는 `src/licensing/keys.py`에 붙여넣는다.

### 8.2 운영 시나리오

| 상황 | 절차 |
|---|---|
| 계약 갱신 | 새 키 발급 → 고객이 앱의 등록 창에 입력 (재설치 불필요) |
| 하드웨어 교체·OS 재설치 | `WRONG_MACHINE` 안내 창에서 **"이 PC로 다시 등록"** 버튼 → 활성화 레코드를 현재 머신 ID로 갱신 |
| PC 이전 | 위와 동일. 대수 제한이 목적이 아니므로 사용자가 스스로 옮길 수 있게 둔다 |
| 키 분실 | 일련번호로 대장 조회 후 재발급 |

**재등록은 공급사 확인 없이 사용자가 직접 한다.** 어차피 키 재사용을 막지 않으므로
(§4.1) 재등록을 막아도 `.activation`을 지우면 그만이고, 막아 두면 하드웨어 고장 시
고객이 도구를 못 쓰는 사고만 남는다. 대신 재등록 시각을 로그에 남겨 추적은 가능하게 한다.

## 9. 인스톨러 변경

`installer/DBMigrationTool.iss`에 다음을 더한다.

- `[Code]`에 `CreateInputQueryPage`로 라이선스 키 입력 페이지
- 입력 즉시 **형식만** 검사(길이·문자셋). 서명 검증은 앱이 한다 — Inno Setup의 Pascal Script로 Ed25519를 구현할 수는 없다.
- 빈 값 허용. 키 없이 설치하고 나중에 앱에서 등록할 수 있어야 한다.
- **`/LICENSEKEY=...` 파라미터를 반드시 지원한다.** BUILD_GUIDE가 안내하는 무음 설치
  (`/VERYSILENT`)에서 입력 페이지는 뜨지 않는다. 이걸 빠뜨리면 사내 배포가 조용히 깨진다.
- **키가 비어 있으면 `license.key`를 건드리지 않는다.** 덮어쓰면 안 된다 —
  §8.2대로 앱에서 갱신 키를 등록한 PC에 `/VERYSILENT` 업그레이드가 돌면
  방금 넣은 키가 빈 값으로 지워져 제한 모드로 떨어진다.
- 저장: **`{app}\license.seed`에 씨앗으로 남기고, 앱이 첫 실행에서 자기
  `%LOCALAPPDATA%`로 옮긴다.**

  인스톨러에서 `{localappdata}`에 직접 쓰면 안 된다 — 그 값은 **설치를 실행한 계정**을
  가리킨다. `PrivilegesRequiredOverridesAllowed=dialog`라 관리자로 승격해 설치하는 경우가
  있고, 그러면 실제로 프로그램을 쓰는 사용자와 다른 계정에 키가 떨어져 앱이 영영 찾지 못한다.
  설치 폴더는 계정과 무관하므로 여기에 두고 앱이 옮긴다.

  씨앗은 지우지 않는다(여러 사용자가 같은 PC를 쓰면 각자 첫 실행에 필요하다).
  제거 시에는 `[UninstallDelete]`로 씨앗만 지우고, 사용자별 `license.key`·`.activation`은
  남긴다 — 재설치 후에도 등록이 유지되어야 한다.

`AppId`는 **바꾸지 않는다**(BUILD_GUIDE의 기존 주의사항).

## 10. 모듈 구조

```
src/licensing/
    __init__.py        LicenseStatus, check_license() 공개 API
    keys.py            내장 공개키 (상수)
    payload.py         키 문자열 인코딩/디코딩, 서명 검증
    machine.py         머신 ID 산출
    activation.py      활성화 레코드 읽기/쓰기, 시계 역행 감지
src/ui/dialogs/
    license_dialog.py  등록·상태 확인 창
tools/
    issue_license.py   발급 (개발사 전용)
```

`check_license()`는 부작용을 최소화하고 순수 함수에 가깝게 둔다 —
파일 I/O는 `activation.py`로 몰아 테스트에서 갈아끼울 수 있게 한다.

## 11. 테스트 계획

기존 테스트 관례(`tests/` 아래 미러 구조)를 따른다.

## 12. 미해결 / 결정 대기

1. **만료 임박 경고 시점** — 30일로 잡았다. 계약 갱신 리드타임에 맞춰 조정 필요.
   구현에는 영향이 없다(상수 하나).
2. **`EXPIRING` 경고 빈도** — 매 실행마다 띄우면 소음이다. 하루 1회로 제한할지.
3. **개인키 보관** — 분실하면 신규 발급이 불가능하고, 유출되면 전체 무력화다.
   보관·백업 주체를 정해야 한다. **착수 자체는 막지 않는다** — 발급 도구가 키 쌍을
   생성하고, 실제 키 생성·보관은 조직이 한다. 다만 첫 고객 배포 전에는 정해져야 한다.

### 결정되어 더 논의하지 않는 것

- **기존 배포본(1.0.0/1.2.1)은 대응하지 않는다.** 업그레이드하면 미인증 → 제한 모드가 된다.
  기존 사용자가 새 마이그레이션을 시작하려면 키를 받아야 한다. 이 전환 비용을 감수하기로 했다.
- **동시 사용을 막지 않는다.** 같은 키가 여러 대에서 활성화되어도 정상 동작한다.
- **PC 바인딩은 유지한다.** 효과는 설치본 폴더 통째 복사 차단 하나뿐이지만 그대로 둔다.
