# 실 DB 수동 확인 체크리스트

- **문서 경로**: `docs/plans/real-db-verification.md`
- **대상 커밋 범위**: `fd2395c`(아카이브 워커 전환) ~ `98a8e0b`(이력 진행량)
- **왜 수동인가**: 아래 항목들은 **실제 PostgreSQL 세션과 실제 스레드 종료**가 있어야만
  드러난다. 자동 테스트는 목(mock)으로 계약만 확인할 수 있고, `conn.cancel()`이
  서버에 실제로 닿는지·워커가 실제로 죽는지는 확인하지 못한다.

## 준비

| 항목 | 값 |
|---|---|
| 소스 | PostgreSQL 9.3, 파티션 **수백~수천 개** 범위 |
| 대상 | PostgreSQL 16 |
| 필수 | 소스 DB에 `ANALYZE`를 **돌리지 않은** 파티션이 최소 1개 (1순위 확인용) |
| 관찰 | 콘솔 로그 창, `pg_stat_activity`, 작업 관리자(프로세스 생존) |

```sql
-- 확인용 세션 모니터 (소스/대상 각각)
SELECT pid, state, query_start, left(query, 80) AS query
FROM pg_stat_activity
WHERE datname = current_database() AND pid <> pg_backend_pid();
```

### 통계 없는 파티션 만들기 (A그룹 확인용)

> **이름 규칙을 꼭 지킬 것.** daily 파티션은 접미사가 **정확히 6자리 `YYMMDD`**여야 한다.
> 8자리(`_29991231`)로 만들면 `infer_partition_range()`가 `(None, None)`을 돌려주고
> **탐색에서 조용히 제외된다**(`src/core/table_types.py:197`). 파티션을 만들어 놓고
> "탐색이 고장났다"고 오해하기 딱 좋다. monthly 계열(`trend_history` 등)은 4자리 `YYMM`.
>
> 연도는 `2000 + YY`로 해석되므로 `991231` = **2099-12-31**이다. 실데이터와 안 겹치는
> 미래 날짜라 테스트에 적합하다.

```sql
-- 1) 물리 테이블 생성 + 데이터 적재
CREATE TABLE history_data_991231 (LIKE history_data INCLUDING ALL);
INSERT INTO history_data_991231 SELECT * FROM history_data_<실데이터> LIMIT 50000;

-- 2) 메타 테이블에도 등록한다.
--    등록하지 않으면 물리 테이블 패턴 fallback 경로로만 발견되어,
--    1차 탐색 경로(partition_table_info)를 확인하지 못한다.
--    from_date/to_date는 **밀리초** 타임스탬프다. table_data는 타입 코드
--    (PH=history_data, PS=point_sec_history, TH=trend_history,
--     ED=energy_display, RT=running_time_history).
INSERT INTO partition_table_info (table_name, table_data, from_date, to_date, use_flag)
VALUES ('history_data_991231', 'PH', 4102326000000, 4102412399999, true);

-- 3) ANALYZE 하지 않는다. reltuples가 0(9.3) 또는 -1(14+)로 남아야 한다.
SELECT relname, reltuples FROM pg_class WHERE relname = 'history_data_991231';
```

**UI에서 날짜 범위를 `2099-12-31`로 맞춰야** 이 파티션이 탐색된다.

정리:
```sql
DROP TABLE history_data_991231;
DELETE FROM partition_table_info WHERE table_name = 'history_data_991231';
```

## A. 데이터 누락 (`39e0f48` · 최우선)

가장 위험한 항목이다. 나머지는 UX 문제지만 이건 **데이터가 조용히 안 옮겨진다.**

- [ ] **A-1** 위에서 만든 `ANALYZE` 안 한 파티션을 포함해 실행
  - 로그에 `통계상 0행이지만 실제 50,000행입니다` 계열 메시지가 뜨는가
  - **실패 신호**: `0행, 건너뜀`으로 넘어가고 체크포인트가 `completed`가 된다
- [ ] **A-2** 실행 후 대상에서 행 수 대조
  ```sql
  SELECT count(*) FROM history_data_991231;  -- 50000이어야 한다
  ```
- [ ] **A-3** 소스에 **진짜 빈 파티션**(0행)을 하나 넣고 실행 — 이건 건너뛰어야 한다
  - **실패 신호**: 빈 테이블에 COPY를 시도하다 오류
- [ ] **A-4** 소스 유저에게서 통계 조회 권한을 뺀 상태로 실행(가능하면)
  - 조회 실패 시 "비었다"고 단정하지 않고 데이터를 옮기는가

## B. 워커 수명 — 프로세스가 죽는가 (`fd2395c`, `dd23b50`)

실행 중인 `QThread`의 마지막 파이썬 참조가 사라지면 **프로세스가 즉사**한다.
이 환경에서 실측한 동작이다. 예외도 스택 트레이스도 남지 않는다.

- [ ] **B-1** 탐색 중 `닫기` — 앱이 살아 있는가
- [ ] **B-2** 탐색 중 `Esc` — 위와 동일
- [ ] **B-3** **창을 열자마자 즉시 `Esc`** (연결 확인 중, 최대 10초 구간)
  - 이 경로가 가장 늦게 발견됐다. 연결 확인 워커가 정리 대상에서 빠져 있었다
- [ ] **B-4** 대상 완료여부 확인 중 닫기
- [ ] **B-5** 검증(행 수 대조) 중 닫기 — **대상 쪽 `COUNT(*)`가 도는 구간**에서
  - 소스만 취소하던 문제를 고친 지점이다. 소스 카운트가 끝난 뒤를 노려야 한다
- [ ] **B-6** 위 전부에서 로그에 `QThread: Destroyed while thread is still running`이 **없는가**
- [ ] **B-7** 마이그레이션 **실행 중**에는 닫기가 여전히 **막히는가** (기존 정책)

## C. 취소가 서버에 닿는가

- [ ] **C-1** 대용량 파티션 탐색을 시작하고 `pg_stat_activity`에서 쿼리 확인
- [ ] **C-2** 창을 닫고 **10초 뒤** 다시 조회 — 그 세션이 사라졌는가
  - **실패 신호**: `idle in transaction` 또는 실행 중 쿼리가 남는다
- [ ] **C-3** 검증 중 닫기 → 소스·대상 **양쪽** 세션이 정리되는가
- [ ] **C-4** 로그에 `조회 작업이 멈추지 않아 분리하고 창을 닫습니다`가 **뜨지 않는가**
  - 이건 성공 신호가 아니라 **실패 증거**다. 협조적 취소가 제한 시간(약 2초) 안에
    끝나지 못해 최후 수단(워커 분리)으로 빠졌다는 뜻이다. 앱은 살지만 원인을 봐야 한다

## D. 세대(generation) — 화면과 실제가 어긋나는가 (`dd23b50`)

- [ ] **D-1** 탐색 중 날짜를 바꾸고 다시 찾기 → 목록이 **새 날짜** 결과인가
- [ ] **D-2** 탐색 중 날짜만 바꾸고 기다리기 → 목록이 **비워지고** 안내가 뜨는가
  - 늦은 결과만 버리고 화면을 그대로 두면 사용자가 새 조건의 결과로 믿는다
- [ ] **D-3** 탐색 중 항목(테이블 타입) 변경 → 위와 동일
- [ ] **D-4** 프리셋 버튼(오늘/어제/최근 7일/30일) → 위와 동일
- [ ] **D-5** 탐색 중 `이전` → `이어서 진행` → `이전` ×2 → `새 작업으로 진행`
  - 목록이 비어 있고, `파티션 찾기`가 탐색 중이면 **비활성**인가
  - **실패 신호**: 목록이 남아 있고, 그걸 실행하면 이력의 날짜와 실제 파티션이 어긋난다
- [ ] **D-6** 실행 후 이력의 날짜 범위와 실제 옮긴 파티션 이름이 맞는가
  ```sql
  -- 로컬 SQLite
  SELECT h.id, h.start_date, h.end_date, c.partition_name
  FROM migration_history h JOIN checkpoints c ON c.history_id = h.id
  WHERE h.id = <방금 실행한 id>;
  ```

## E. 진행량 표시 (`98a8e0b`)

- [ ] **E-1** 실행 → 중간에 취소 → 창 닫기 → 다시 열기
  - 재개 안내가 `N / 약 M rows (P%)` 형태인가
  - **실패 신호**: `N / 0 (rows)`
- [ ] **E-2** 재개해서 끝까지 실행 → 다시 열기
  - 진행량이 **줄어들지 않았는가**. 이게 원래 결함이었다
- [ ] **E-3** 이 수정 **이전에** 생긴 미완료 이력으로 열기
  - `N rows 처리됨`(분모 없음)으로 뜨는가. `/ 0`이 없어야 한다
- [ ] **E-4** 완료 후 로컬 DB 확인
  ```sql
  SELECT id, status, total_rows, processed_rows FROM migration_history ORDER BY id DESC LIMIT 5;
  ```
  `total_rows`가 0이 아니고, `processed_rows`가 체크포인트 합계와 맞는가

## F. 일시정지 (`dd23b50`)

- [ ] **F-1** COPY 모드 = **Python COPY**로 실행 → `일시정지` → 진행이 곧 멈추는가
- [ ] **F-2** COPY 모드 = **Server-side** 또는 **auto**로 실행 → `일시정지`
  - 문구가 `일시정지 요청됨 · 진행 중인 파티션이 끝나면 멈춥니다`인가
  - 그 파티션이 끝난 뒤 **실제로 멈추는가** (다음 파티션으로 안 넘어가야 한다)
  - **실패 신호**: 화면만 '일시정지'이고 끝까지 계속 돈다 (이게 원래 결함)
- [ ] **F-3** `재개` → 이어서 진행되는가
- [ ] **F-4** 일시정지 상태에서 `작업 취소` → 멈추는가 (교착 없이)
- [ ] **F-5** 아카이브 다이얼로그에 일시정지 버튼이 **없는가** (의도된 제거)

## G. 행 수 표기 (`dd23b50`)

- [ ] **G-1** PostgreSQL 소스로 탐색 → 목록이 `약 1,234 rows`인가
- [ ] **G-2** `ANALYZE` 안 한 파티션이 `행 수 미상`으로 뜨는가
  - **실패 신호**: `0 rows` — 사용자가 빈 파티션으로 읽고 체크를 푼다
- [ ] **G-3** 탐색 **속도**: 예전에는 파티션당 `COUNT(*)` 전수 스캔이 돌았다.
  수백 개 범위에서 체감 차이가 나는가
- [ ] **G-4** 아카이브 **가져오기**(파일→DB) 탐색 → `약` 없이 정확한 수인가
  - 매니페스트의 행 수는 내보낼 때 실제로 센 값이다
- [ ] **G-5** 선택 합계 라벨과 요약 화면도 같은 규칙을 따르는가

## 실패했을 때

1. 로그 창 전체를 복사한다 (화면은 최근 5,000줄만 남지만 파일에는 전부 있다)
2. `pg_stat_activity` 스냅샷을 뜬다
3. 로컬 SQLite의 해당 `migration_history` + `checkpoints` 행을 덤프한다
4. 어느 항목(A-1 등)에서 무엇이 기대와 달랐는지 적는다
